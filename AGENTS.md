## ⚠️ СТРОГИЕ ПРАВИЛА РАБОТЫ (ОБЯЗАТЕЛЬНЫ К ИСПОЛНЕНИЮ):
1. **КОД НЕ ПИСАТЬ И НЕ МЕНЯТЬ БЕЗ ПРЯМОГО ЯВНОГО УКАЗАНИЯ ПОЛЬЗОВАТЕЛЯ.**
   * **СТРОГО ЗАПРЕЩЕНО** писать код, создавать новые файлы с кодом или редактировать существующие файлы без прямого, недвусмысленного указания пользователя (например: «пиши код», «приступай к кодированию», «создавай файлы»).
   * Слова «Continue», «Продолжай» или описание общей задачи **НЕ ЯВЛЯЮТСЯ** командой писать или менять код. В таких случаях разрешается только проводить анализ, исследование и предлагать план/варианты решений.
   * Никаких самостоятельных правок, оптимизаций, рефакторинга или исправления кода.
   * Если обнаружена ошибка, предложено решение или требуется реализация — сначала описать всё пользователю и дождаться прямого указания («пиши код», «приступай»).
2. **СТРОГОЕ ПРАВИЛО РАБОТЫ С GIT: НИЧЕГО НЕ ПУШИТЬ И НЕ КОММИТИТЬ БЕЗ ПРЯМОГО УКАЗАНИЯ ПОЛЬЗОВАТЕЛЯ.**
   * **СТРОГО ЗАПРЕЩЕНО** делать любые коммиты и отправки (`git commit`, `git push`, сброс изменений) без прямого явного указания пользователя («закоммить», «запушь», «залей на гит»). Без прямого указания пользователя ни локальные коммиты, ни удаленные пуши НЕ выполняются.
   * Незавершенный или несогласованный код не коммитится и не пушится.
   * **Атомарность commit + push**: коммиты и пуш выполняются строго совместно и атомарно в один шаг.
   * **Для экономии токенов и надёжности:** все коммиты выполняются строго через скрипт `python git_commit.py "<сообщение>" [-d "<описание>"]` (или батники `git_sync.bat` / `git_push.bat`). Скрипт по умолчанию выполняет полный цикл: индексация (`git add -A`) -> коммит с подавлением шума CRLF -> отправка (`git push origin main`) на GitHub. Краткий статус: `python git_commit.py -s`.
3. **КОНВЕНЦИЯ КОМАНД ПОЛЬЗОВАТЕЛЯ:**
   * **«исправить» / «исправьте» / «почините»**: команда на немедленное устранение багов и ошибок в коде без повторного переспроса.
   * **«приступайте»**: команда на реализацию нового предварительно обсужденного функционала.
   * **БЕЗ ЭТИХ КОМАНД**: Строго режим обсуждения и консультаций.

## Окружение и команды сборки
* **Среда разработки:** Windows 10/11, Microsoft Visual Studio Community 2026.
* **MSBuild 2026:**
  ```powershell
  & "C:\Program Files\Microsoft Visual Studio\18\Community\MSBuild\Current\Bin\MSBuild.exe" ELECTROMAGNETIC_TOOLS_3.0.sln /p:Configuration=Release /p:Platform=x64
  ```
* **Штатный скрипт сборки (подавление шума компилятора):**
  ```powershell
  python build.py
  ```
* **Компактная сборка и smoke-проверка запуска:**
  ```powershell
  python verify.py
  python verify.py --full
  python verify.py --run --config Debug
  python verify.py --data "C:\EXP\CARTOGRAF\Dataout_cartograf_2_03_12_25.bin"
  ```
  `verify.py` выводит только краткий итог, проверяет раннее аварийное завершение и останавливает только запущенный им экземпляр приложения.
* **Полная проверка CSV и обеих конфигураций:**
  ```powershell
  python verify.py --full --csv-check
  python test_csv.py --config Release
  ```
  `test_csv.py` использует временную папку, сравнивает все поля CSV с исходными байтами, проверяет семейства 3Tx/4Tx/5Tx, Картограф, BIN/DEV, legacy GP 240, Min–Max, NaN/Inf и защиту от перезаписи. Стендовые файлы из `C:\EXP` проверяются при наличии; их отсутствие явно отмечается как SKIP.
* **Экспорт без GUI:**
  ```powershell
  .\x64\Release\ELECTROMAGNETIC_TOOLS_3.0.exe --export-csv "input.bin" "output.csv"
  .\x64\Release\ELECTROMAGNETIC_TOOLS_3.0.exe --export-csv "input.bin" "range.csv" --frames 100 200
  .\x64\Release\ELECTROMAGNETIC_TOOLS_3.0.exe --export-csv "input.bin" "temperature.csv" --temperature 20 50
  ```
  Оба предела включены; `--frames` — индексы записей 0..N−1, `--temperature` — фильтр по температурной оси в исходном порядке. Имя выходного файла должно быть новым.

## Контракт полного CSV-экспорта
* `em_cartograph_v1`: кадр `ALL_DATA` 3072 байта, 824 столбца, все поля двух блоков DATA и RAW_DATA, включая packed out_arr и 16 комплексных секторов для каждого Tx/Rx/частоты.
* `em_gp_v1`: `GP_DATA` 320 байт, 86 столбцов; для старых записей без размера в сигнатуре используется 240 байт, как в `AIR_TEMP_1.0/variable.cpp::get_sonde_id`. Картограф LWD_4Tx использует эту общую схему.
* CSV: ASCII-совместимый UTF-8 без BOM, запятая-разделитель, точка в числах, 9 значащих цифр для round-trip float32. NaN/Inf записываются как `nan`, `inf`, `-inf`.
* Первые столбцы: `schema,row_index,sonde_type,sonde_number,tx_count,record_bytes`. `row_index` — индекс исходной записи; `frame`/`f400_frame`/`f2000_frame` — счетчики из самого прибора.
* Имена полей структуры сохраняются с префиксами `f400_`/`f2000_`, `tx1_`..`tx5_`, `rx_l_`/`rx_r_`; комплексные значения разделены на `_re`/`_im`, секторы нумеруются 0..15. Исходные значения не пересчитываются и не зависят от настроек графиков или метрологии. Это отдельный контракт, не обещающий совместимость со старым калибровочным RAW CSV.
* Отсутствующие Tx и поля за пределами короткой GP-записи — пустые ячейки, не нули. Вычисляемые только наземной программой гармоники и производные не добавляются к исходным данным.
* Экспортер не перезаписывает существующие файлы (включая исходный бинарник), удаляет собственный частичный CSV при ошибке записи. Python читает таблицу стандартным `csv.DictReader`; зависимости для тестов не нужны.
* При открытии BIN/BIV/DEV проверяются все Signature (для Картографа оба частотных блока) и кратность длины размеру записи с учетом преамбул. Изменение Signature/размера и неполный кадр запрещают открытие. Ошибка содержит индекс и смещение; предыдущая сессия сохраняется. Эти сценарии включены в `--csv-check`.

## Обновление переносимой программы
* `UpdateAgent.cs` — отдельный .NET updater и интерфейс настройки/проверки. Собирается штатным MSBuild target в `EmUpdate.exe` рядом с главным EXE, без Python на компьютере оператора. При распространении папки обязательно включать оба EXE.
* Меню «Справка»: ручная проверка, отключаемая проверка при запуске (по умолчанию выключена), настройки FTP. Сеть и распаковка выполняются вне UI-потока; установка только после подтверждений скачивания и закрытия приложения.
* Канал — отдельный каталог `ELECTROMAGNETIC_TOOLS_3.0` рядом с каналом старого SONDE_TEST. По прямым командам пользователя каталог создан и опубликован первый релиз 3.0.0.0, build=1: `release-1-39899cb6e36a.zip` (130497 байт), затем `manifest.json`. Локальный пакет: `x64/ReleasePackage-1`. Следующий релиз должен иметь build >= 2. Автотесты используют только временные папки и FTP на loopback.
* Публикация build=1 проверена обратным скачиванием: манифест побайтно совпадает, ZIP скачан Python ftplib в passive mode, SHA-256 `6ba0f5915d7f1bd892ebb5a0e5c9e7c88ee0a699cd7b2664b76368fe17dfc460`; `EmUpdate --prepare` проверил состав/хеши EXE без установки в рабочую папку. ВАЖНО: ранние таймауты скачивания ZIP сразу после публикации оказались транзиентными. Диагностика 29.10.2026 (прямой Wi-Fi bind vs VPN-туннель, без изменения маршрутов) показала: манифест и ZIP 91 МБ скачиваются и проходят SHA-256 на обоих маршрутах и через ftplib, и через штатный FtpWebRequest с параметрами updater; VPN лишь замедляет (до ~56 c vs ~40 c). Ручная проверка установки через UI остается за оператором.
* FTP-клиент задает `FtpWebRequest.Proxy = null` для прямого подключения, не изменяя системные настройки Windows. Не убирать эту строку: системный HTTP-прокси мешал FTP-запросам. `test_update.py` проверяет явно отключенный proxy и загрузку при принудительном неработающем default proxy (.NET Framework 4.8).
* По решению пользователя цифровой подписи нет: `authentication=none`. SHA-256 обнаруживает повреждение пакета, но не подтверждает его подлинность; предупреждение есть в интерфейсе. Ключи не создавались.
* Учетные данные не встроены в код. Ввести их один раз через «Справка → Настройки FTP-обновления...». Настройки хранятся в `%LOCALAPPDATA%\AMK_Gorizont\ElectromagneticTools3\<installation_hash>\updates.json`; пароль защищен DPAPI CurrentUser. После смены компьютера/учетной записи или пути папки доступ задается заново. Не выводить пароли в чат/логи и не коммитить их.
* Манифест `schema=1`, `product=ELECTROMAGNETIC_TOOLS_3.0`, `platform=x64`, монотонный `build`, версия сборки, UTC-дата, описание, имя/размер/SHA-256 ZIP и каждого файла. Установленный манифест — `release.json`, он меняется только после успешной замены всех файлов. Для старой папки без него номер сборки равен 0.
* Допустимы только главный EXE, `EmUpdate.exe`, соответствующие `.exe.config` и файлы `scripts/*.py` (плоско, без вложенных папок и `..`) — по правилу пользователя все нововведения входят в обновление. Другие пути, дополнительные/повторяющиеся файлы ZIP, ссылки, неверный продукт/платформа, хеши/размеры и старые сборки отклоняются. Пользовательские настройки, метрология, BIN/CSV, журналы и Python Runtime в пакет не входят.
* Updater запускается из временной папки, ожидает завершения конкретного PID с проверкой времени старта и пути EXE, проверяет отсутствие других экземпляров и берет блокировку установки. Замена каждого файла атомарная; перед заменой создается `.em-update-backup/<id>` с журналом и контрольными суммами резервных копий. Ошибка установки вызывает откат измененных файлов. Резервные копии автоматически не удаляются.
* При аварийном обрыве питания/процесса незавершенный журнал обнаруживается при запуске, новые установки блокируются. Восстановление: закрыть приложение, запустить **копию EmUpdate.exe из другой папки** с `--recover "<папка резервной копии>"`. Восстановление не предназначено для отката уже успешно установленных релизов.
* Локальная установка для стенда, без перезапуска GUI: `EmUpdate.exe --install-local "manifest.json" "release-<build>-<id>.zip" "<целевая папка>"`. Updater должен находиться вне целевой папки. Использовать только тестовую копию папки, если установка не запрошена оператором.
* `EmPublish.cs` — отдельная утилита публикации релизов для разработчика (`EmPublish.exe`), собирается тем же штатным шагом MSBuild рядом с EXE. Публикует строго из `x64\Release` (источник = папка самого EmPublish.exe): канал приложения (`manifest.json`) и Python Runtime (`python-runtime.json` из `python_runtime`). GUI по двойному клику: канал → номер сборки → описание → «Собрать пакет» → «Опубликовать». CLI для BAT: `EmPublish.exe [--runtime] --build N --output DIR --desc TXT [--publish]`; без `--publish` только локальный пакет. FTP-доступ тот же, что у программы (`updates.json`, DPAPI), можно ввести и сохранить в форме. Порядок публикации как у `publish_release.py`: проверка удаленного манифеста (продукт/канал/монотонный build), ZIP под временным именем → rename, манифест последним → rename. EmPublish.exe НЕ входит в allowlist обновления и не уходит операторам.
* Полная проверка:
  ```powershell
  python verify.py --full --csv-check --update-check --python-check
  python test_update.py --config Release
  ```
  `test_update.py` проверяет подготовку/установку, блокировки и откат, ожидание PID, защиту данных, восстановление журнала, некорректные ZIP/манифесты, скачивание через локальный FTP и порядок публикации через mock. Внешний FTP не используется.
* Локальная подготовка релиза:
  ```powershell
  python publish_release.py --build 2 --desc "Описание релиза" --output "C:\Releases\EMTools_2" --no-upload
  ```
  Родительская папка должна существовать; папка результата должна быть новой. По умолчанию скрипт сначала выполняет сборку Release и проверки. Версия берется из метаданных EXE; `build` задается отдельно и обязан расти. Подготовка не изменяет текущую установленную версию.
* **Публикация только по отдельному прямому разрешению:** добавить `--publish` вместо `--no-upload`; доступ передать локально через `EM_FTP_USER` и `EM_FTP_PASSWORD`. Сначала отправляется уникальный ZIP через временное имя, затем последним переименовывается новый `manifest.json`. Номер серверной сборки проверяется до отправки. FTP-каталог должен уже существовать; автоматического создания нет. Git push и публикация FTP — разные операции, одна не разрешает другую.

## Отдельный Python Runtime
* `PythonRuntime.cs` компилируется вместе с `UpdateAgent.cs` в EmUpdate.exe. В «Справке» доступны отдельная установка/обновление среды и локальная проверка Python. Загрузка не требует заранее установленного системного Python.
* Компонент `python-runtime`, собственный `python-runtime.json` и уникальный `python-runtime-<build>-<id>.zip` в том же FTP-каталоге. Номера сборок приложения и Python независимы. Публикация Runtime не заменяет `manifest.json` приложения; `upload_release` проверяет соответствие компонента каналу.
* `publish_python_runtime.py` использует **готовую portable-среду**, проверяет ее через EmUpdate.exe, не скачивает pip/пакеты из Интернета и не изменяет исходную среду. Исключает кэши, тесты и локальный runtime-release.json; SHA-256 рассчитывается по фактически упакованным байтам. Пакет проверяется клиентским `--runtime-prepare` до возможной публикации. По умолчанию только локальная упаковка, `--publish` требует отдельного разрешения и доступа через EM_FTP_USER/EM_FTP_PASSWORD.
* Подготовленный локальный пакет: `x64/PythonRuntimePackage-1/python-runtime.json`, архив `python-runtime-1-7dc455027d64.zip`, 91380209 байт, 6650 файлов, SHA-256 `9e92a04caffe1c1f9f1e199f63bb75b465ae0c29b8e57d1c6eaf0336ef35d21a`. Источник — готовый python_runtime старого проекта. Python 3.11.9 x64, NumPy 2.4.6, SciPy 1.17.1, pandas 3.0.6, Matplotlib 3.11.2, Tcl/Tk 8.6.14. **По прямой команде пользователя пакет опубликован на FTP**, `python-runtime.json` размещен последним. На сервере подтверждены размеры ZIP 91380209 и манифеста 1234395 байт. Манифест приложения побайтно не изменился (SHA-256 `6df1fcf4173eb30383d9ece3aa42e3b7bc5373dfc9a6cd5c13ecc51a487355ee`), app build=1 не заменялся. Пользователь пересобрал программу локально; для доставки этих меню другим операторам нужен следующий app-релиз (build >= 2). Следующий Runtime должен иметь build >= 2.
* Архив содержит пути относительно корня среды. Установка меняет только управляемую папку `python_runtime`; корневые EXE, release.json приложения, настройки, метрология и CSV не затрагиваются. Старая среда целиком переносится в `.em-update-backup/<id>/python_runtime`. Не хранить операторские данные/аналитические скрипты внутри среды; прежние нестандартные файлы сохраняются в резервной копии, а не переносятся в новую среду.
* До замены проверяются пути/ссылки/дубликаты, размеры/SHA-256 всех файлов, а затем в отдельной входящей папке запускается реальный Python с `-I -B`: импорты и версии всех библиотек, математика NumPy/SciPy/pandas, график Matplotlib Agg, скрытое окно Tkinter. Модули обязаны находиться внутри Runtime. Проверка повторяется после переименования папки; при ошибке старая среда восстанавливается. Работающие процессы этого Python блокируют установку, чужие процессы не завершаются. Есть журнал/восстановление через общий `--recover`.
* Ограничения: ZIP до 256 MiB, распаковка до 1 GiB, до 20000 файлов, манифест до 16 MiB. Не допускаются абсолютные пути, `..`, ADS, зарезервированные имена Windows, корневые manifest.json/runtime-release.json и ссылки. Цифровой подписи по решению пользователя нет. Активный режим сервер отклоняет (501) — использовать только passive. Сервер не объявляет HASH; удаленный SHA-256 Runtime подтвержден обратным скачиванием и локальным хешированием (29.10.2026, маршруты VPN/Wi-Fi — см. SESSION_STATE). Установка Runtime через UI проверена только локальными тестами; реальная установка — за оператором.
* Проверки:
  ```powershell
  python verify.py --full --csv-check --update-check --python-check
  python test_python_runtime.py --config Release --real-package "x64/PythonRuntimePackage-1"
  .\x64\Release\EmUpdate.exe --python-probe "C:\Path\To\python_runtime"
  ```
  Тесты Runtime используют моделируемый интерпретатор для отказов/отката; `--real-package` дополнительно устанавливает настоящий пакет в удаляемую временную папку и проверяет настоящие библиотеки. Не выдавать mock-проверку за проверку реального Python.
* Локальная подготовка следующего пакета (родитель выходной папки должен существовать):
  ```powershell
  python publish_python_runtime.py --runtime-dir "C:\Path\To\python_runtime" --build 2 --output "C:\Releases\PythonRuntime_2" --desc "Описание среды" --no-upload
  ```
  Для автономной установки в тестовую папку: `EmUpdate.exe --runtime-install-local "python-runtime.json" "python-runtime-<build>-<id>.zip" "<папка приложения>"`.
